## 두 오류의 원인과 수정

**상세 주소의 원본 파일명.** 이름은 업로드 때 이미 정규화해 `job.json`에 저장하지만 두 화면은 Router 전달값만 읽었다. 상태 GET과 완료 결과 GET에 nullable `original_filename`을 추가했다. 결과 조회가 완료 여부 확인을 위해 읽은 메타데이터를 재사용한다. 각 화면은 서버 이름, 이동 경로에서 전달한 이름, 기존 대체 문구 순으로 표시한다. 기존 업로드 응답·저장 파일·리포트 구조를 유지하며 예시 경로는 실제 API를 호출하지 않는다. 같은 UUID로 새 탭 직접 접근과 새로고침을 비교했다. [API 계약](../api_contract.md) · [전후 화면](../../outputs/evidence/part6_5_final_service_validation/evidence_notes.md)

**이력 검색어 복원.** 실제 Chrome에서 검색 제출 직후 주소에 `search=Dashcam-Rear`가 있었다. 바로 상태를 선택하면 주소는 `?status=completed`가 됐고 입력칸에만 검색어가 남았다. 결과에서 뒤로 돌아오자 손실된 URL을 따라 입력칸도 비었다. 새 렌더 전에 호출된 상태·정렬 핸들러가 이전 렌더의 쿼리를 바탕으로 다음 주소를 만든 것이 원인이었다. 조건을 바꾸는 순간 현재 브라우저 주소의 쿼리를 읽어 다음 변경을 적용했다. 검색 입력 초안과 URL에 확정된 조건, 목록 요청 취소 방식은 유지했다. 수정 전 Edge 회귀도 같은 연속 조작에서 `?sort=oldest`만 남는 실패를 재현했다. 수정 후 실제 Chrome에서 상세 → 뒤로 → 새로고침 → 초기화 → 뒤로 흐름 5/5, 재개 후 Edge의 독립 반복 5/5였다. [수정 전 URL 추적](../../outputs/evidence/part6_5_final_service_validation/history_trace.json) · [수정 후 URL 추적](../../outputs/evidence/part6_5_final_service_validation/history_trace_1795768325458.json)

## 예외 처리와 Windows 종료

실제 격리 HTTP에서 잘못된 확장자는 415, 손상 MP4는 422, 없는 작업은 404, 실패 작업의 결과·내보내기는 409였다. 재기동 후 브라우저에서 결과 요청 및 대표 JPEG의 첫 연결을 차단한 다음 재시도해 실제 서버 응답과 1920px 이미지를 복구했다. 크기 초과·청크 제한, 미완료 작업, 손상 검토 파일, 정상 무탐지·조회 실패의 구분, 내보내기 재시도는 임시 저장소 Python 테스트와 Mock 브라우저 테스트에서 확인했다. [실제 응답 코드](../../outputs/evidence/part6_5_final_service_validation/audit.json) · [재시도 및 복원 기록](../../outputs/evidence/part6_5_final_service_validation/restart.json)

기존 Windows 서버 팩터리와 HTTP 종료 제한 3초를 사용했다. 종료 요청부터 서버 반환까지 유휴 0.146초, 영상 정지 탭 0.203초, 재시작 후 영상 재생 중 0.205초였다. 별도 실제 CUDA 작업과 합성 대기 작업이 있을 때는 첫 연결 거절이 0.563초, 서버 반환이 8.421초였다. GPU 워커는 진행 작업을 완료했고 대기 작업은 `failed/interrupted`가 됐다. 재기동 후 두 상태와 최종 비교 작업의 결과·검토를 다시 읽었다. 종료 입력은 격리 Uvicorn의 정상 종료 플래그였다. 실제 콘솔 신호 시험은 이전 기록에 있다.
